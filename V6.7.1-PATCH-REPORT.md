# BSR Vault v6.7.1 Patch Investigation Report

## Scope
Targeted investigation of exactly 3 reported regressions.

## BUG 1 — JioPOS Autofill dropdown/chips
Status: **ROOT CAUSE NOT CONFIRMED — NO CODE CHANGE MADE**.

Evidence from current v6.7 source:
- `BSRAutofillService.kt:148` computes `useInline` only when Android 11+ and an inline request exists.
- `BSRAutofillService.kt:163` passes `null` inline presentation when no inline request exists.
- `BSRAutofillService.kt:165-172` still calls `Dataset.Builder` and `setValue()` for every username/password field.
- `BSRAutofillService.kt:124-130` explicitly falls back to `ds.setValue(id, value, pres)` when inline is unavailable.
- `BSRAutofillService.kt:160` creates the standard `RemoteViews` presentation.

Comparison against the supplied v6.5 source shows the same `buildResponse()` / `setVal()` presentation path and the same `InlineHelper.kt` implementation. Therefore the hypothesis that v6.7 skips standard dropdown presentation when inline request is absent is **not supported by the source**.

The v6.7 changes in `BSRAutofillService.kt` are matching precedence, SaveInfo flag, browser-save guard, and appPackage persistence; none changes the standard Dataset presentation path.

No speculative Autofill change was made.

## BUG 2 — Edit strength bar
Status: **FIXED**.

`AddEditActivity.kt:87` no longer aborts initialization when `R.id.strengthBar` is absent. The lookup is now optional:

```kotlin
strengthBar = findViewById(R.id.strengthBar)
```

The XML contains no `@+id/strengthBar`, confirming the original abort condition.

## BUG 3 — Diagnostics version
Status: **FIXED**.

`AutofillLog.kt:41` and `:73` no longer use hardcoded `v6.5`. Both now use `BuildConfig.VERSION_NAME`.

## Build verification

`./gradlew clean assembleDebug --stacktrace`

It could not run because the Gradle wrapper attempted to download Gradle 8.2 from `services.gradle.org`, but this environment has no network/DNS access. Therefore **BUILD SUCCESSFUL is NOT claimed**.
